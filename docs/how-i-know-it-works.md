# 一个人写代码时，怎么知道它是对的

做 [Dolos](https://github.com/parthenon-labs/dolos) 的过程里，让我卡最久的从来不是"不会写"，
而是"写完了，但不知道它对不对"。

这个项目没有同事、没有 code review、没有 QA。所有 bug 只有两种下场：
被我自己抓住，或者被玩家抓住。而回头看，**几乎每一个难缠的 bug 都有同一个特征：
代码看起来是对的，测试是绿的，程序也没报错。**

这篇文章讲的是这类 bug，以及我最后是靠什么抓住它们的。

---

## 一、绿色的对勾不等于验证过

德州扑克里有两处算错就直接把玩家的钱分错：牌力评估和边池分配。
我给它们写了几十条用例，跑出一片 `✓`。

然后我发现，**其中三条用例是错的，而代码是对的。**

最典型的一条，我想验证"七张里同时成顺子和同花时必须选同花"：

```ts
beats('七张里选同花不选顺子', '5s 6s 7s 8s 9h Th 2d', '5h 6d 7s 8c 9h 2s 3d')
```

它通过了。但仔细看那手牌：黑桃只有 `5s 6s 7s 8s` 四张——**根本没有同花。**
这条用例实际比较的是两个顺子，关于"同花优先于顺子"它什么都没验证，
却在输出里留下一个让我安心的对勾。

另外两条是边池的。我预期分层后是两个池，实际代码把资格相同的相邻层合并成了一个——
**合并逻辑是我自己十分钟前写的**，写用例时却按未合并的形态写了预期。

从那以后我给自己加了一条规矩：

> 写完一条用例，问一句"它失败的时候会输出什么"。
> 答不上来，这条用例就是装饰品。

一条永远不会红的用例，比没有用例更糟——它占着"这里已经验过了"的位置。

---

## 二、比用例更靠得住的是不变量

用例只能覆盖你想到的情况。真正把我从边池 bug 里捞出来的是两条**不变量**：

**筹码守恒。** 一手牌开始前和结束后，所有人的筹码总和必须精确相等，一分不多不少。
这条能兜住绝大多数分池错误，因为把钱分错几乎必然破坏它。
更重要的是它不需要我预先想到"三人不同额度 all-in 且其中一人中途弃牌"这种局面——
随机跑就行了，错了它自己会炸。

所以 `settle()` 里那句是**抛异常，不是打日志**：

```ts
if (totalWon !== totalPot) {
  throw new Error(`底池分配不守恒：池共 ${totalPot}，分出去 ${totalWon}。这是 bug，不要吞掉`)
}
```

分池写错时它当场炸掉，而不是等玩家发现自己少了钱。
一个安静地把钱算错的程序，比一个崩溃的程序危险得多。

**样本量本身也要断言。** 边池只在 all-in 时出现，而在均匀随机的对局里 all-in 不够密。
我一开始的压力测试"通过"了，但里面几乎没有边池——它验证的是一条我不关心的路径。

修法是刻意用参差不齐的起始筹码把 all-in 逼出来，并且**把覆盖率本身写成断言**：

```ts
if (sidePotHands < 50) fail('边池样本太少，这轮压力测试没有真正覆盖到边池')
```

现在的数字是 4000 手随机牌局里 2698 手产生边池。哪天有人改了参数让这个数字掉下去，
测试会红——而不是继续绿着，却什么都没测。

## 三、有时候"能验证"比"快"更值钱

七张牌里挑最好的五张，标准做法是查表：预计算一张巨大的查找表
（常见实现从几百万项到三千万项不等），一次哈希出结果，比暴力枚举快几十倍。

我用了暴力枚举——穷举 C(7,5)=21 种组合，每种打分取最大。

理由很简单：**那样一张表，我没有任何办法用眼睛确认它是对的。**
它错了的表现不是崩溃，是某一类罕见牌型被判错，而那可能几万手牌才出现一次，
出现时也只是"有人觉得自己应该赢"。而 21 次组合每手牌不到 10 微秒——
真实瓶颈根本不在这里，我花那几十倍的性能什么也换不来。

这不是"不要优化"，是**在还不知道瓶颈在哪的时候，先选看得懂的那个**。
真到了性能吃紧那天，我有一份能跑的暴力实现当基准，
可以拿它逐张验证查表版——这时候查表才是安全的。

## 四、假的东西必须和真的说同一种协议

项目里有个"假 LLM"：不联网、瞬间返回，但走完整的提示词构造、结构化输出解析、
非法动作重试、防泄漏审查。它的职责不是"会玩"，是让我在没有 API key 的情况下
验证**管线本身**是通的。

分清"管线坏了"和"模型不行"，是这类项目里最省时间的一件事。

后来我改了一处编号约定：提示词里的玩家编号从 0 起始改成 1 起始。
假 LLM 是靠正则从 schema 描述里抠范围的（`范围 0-N`），描述改了，它没跟上，
于是退回默认值，再减 1——**产生了负数玩家编号**。

我是怎么发现的？200 局里的非法动作数从 **38 涨到 1268**。

没有这个数字，我大概率不会发现：游戏照常跑完，引擎照常把非法动作纠正掉，
胜率看起来也还行。这引出另一件同类的事——

早些时候我用一个**错误的 API key** 跑了一整局，它跑完了，
还给出了一个看起来很合理的胜率。原因是 SDK 在构造时不校验凭证，
而请求失败被我用来兜住"模型给了非法动作"的那个 try/catch 一并吞掉了。
整局跑的全是兜底动作，而输出里没有任何异样。

修法有两条，第二条更重要：

1. 启动时就校验凭证，缺了直接退出并给出能照做的命令
2. **把"调用报错"和"非法动作"分开统计**

它们混在一起时，一个坏掉的 key 会伪装成"模型很笨"——
而这两种问题的排查方向完全相反。

## 五、两套约定并存，没有任何一行代码是错的

同一个项目里，引擎内部玩家编号从 0 开始，界面显示从 1 开始。

于是模型说"0 号有问题"，而界面上根本没有 0 号玩家。玩家会指错人。
你去读任何一个文件，都找不到写错的那一行——**每一处单独看都是自洽的。**

统一成"对内 0 起始、对外一律 1 起始，只在两处转换"之后，
这个改动**同时打破了三个地方**：

- 防泄漏层从发言里抠出的编号变成 1 起始，却拿去和 0 起始的角色知识比对。
  整层**静默偏一位**：该拦的放行、不该拦的拦下，而且只影响部分发言，看日志发现不了
- 假 LLM 的正则（就是上一节那个）
- 防泄漏层自己的用例——它们还在用旧约定，**会继续通过，并且什么都不证明**

最后一条是最阴的：改约定的时候，最先该改的就是那些用来保护约定的测试，
但它们恰恰是最容易被忘掉的，因为它们是绿的。

## 六、直觉很自信，但它算不了数

游戏里六个人围一张圆桌，第一人称视角下坐在你两侧的人会出画。

直觉方案是"把座位排成弧形"——我这么想，提需求的人也这么想。

我先算了一下。座位均分整圈、人人朝桌心时，最边上那个人相对你视线的偏轴角是：

```
90° − 180°/n
```

六个人就是 60°，而当时的水平半视角只有 42.7°——确实出画。

但关键在于：**这个角度只取决于座位之间的角间距。**
弧形是把同样多的人压进更小的张角，间距只会变小。
下面这组数字是在相机已经后拉 1.3 倍座位半径的前提下量的：

| 方案 | 邻座偏轴角 |
|---|---|
| 整圈六人 | 47.3° |
| 排成 180° 弧 | **73.8°**（更糟） |
| 排成 300° 弧 | 47.3°（六人排 300° 弧的间距同样是 60°，和整圈是同一个几何） |

弧形不但没解决问题，还会让各个座位的视野不再等价——
在一个靠观察别人做决策的游戏里，那是把座位变成了信息优势。

真正有效的是把相机沿径向后拉，以及**按画面比例实时算 FOV**：
同一个 63° 在 16:9 下水平半视角是 47.5°，在 3:2 下只有 42.6°。
写死一个数字，换台笔记本或者把窗口拖窄就会把人切掉——
**而这种 bug 在自己的显示器上永远复现不出来。**

还有一条是驱动着跑才发现的：余量必须按**肩宽**算，不能按座位中心点。
角色半宽 0.3 米、距离 2.9 米，自己就占 5.9°。
只看中心点的话，数字上"在画面内"，画面上是被切掉半个身子的。

## 七、性能问题也要量，不能猜

场景一度跑到 9.7 FPS。我列了三个嫌疑人：

- 四十多盏动态光源
- 反射地板
- 后处理（Bloom / 色差 / 噪点 / 暗角）

凭直觉，后处理和反射地板都很"重"。实际逐个关掉测下来：

**反射地板和后处理加起来只值大约 1 FPS。灯是全部的代价。**

修法是给光源做预算——只让最近的 N 盏可见。但这里有个反直觉的细节：

> 可见光源的**数量必须恒定**。

three.js 会按场景里的灯数编译着色器，数量一变就重新编译。
如果按距离动态增减可见灯数，玩家每走几步就会卡一下——
而且这种卡顿看起来像"随机掉帧"，极难归因。
正确做法是可见数量固定，只换是哪几盏。

最后 70.8 FPS。而如果我按直觉先去砍后处理，砍完画面变丑，帧数纹丝不动。

## 八、最难查的一次：整个画面全黑

有一次整个画面变成纯黑。我做的第一件事是把后处理的各项强度调成 0——
画面还是黑的，于是我排除了后处理。

**这个排除是错的。**

真正的原因是某个几何体的顶点法线里出现了 `NaN`（对插值出来的圆锥顶点法线做归一化，
长度为零时除出 `NaN`），而 Bloom 的降采样链把这一个 `NaN` 像素扩散到了整帧。

我的排查之所以失效，是因为 **`NaN × 0` 仍然是 `NaN`**。
把强度调成 0 并不能阻断 `NaN` 的传播，所以"关掉它还是黑的"完全不能作为排除依据。

修法是给归一化加长度保护：

```ts
const safeNormalize = (v) => (v.lengthSq() > 1e-12 ? v.normalize() : fallback)
```

教训不在于这个具体的 bug，而在于：**排除法的前提是"关掉它"真的等于"它不参与"。**
在浮点、着色器、异步这几个地方，这个前提经常不成立。

---

## 这些手段的共同点

回头看，它们其实是同一件事的不同侧面：

- **不变量**优于用例——因为它不要求你预先想到那个局面
- **可读性**优于性能——在还不知道瓶颈之前
- **失败要响**——`throw` 而不是 `console.log`，安静的错误是最贵的
- **覆盖率本身也要断言**——否则测试会在你不知道的时候变成空跑
- **数字优于直觉**——尤其是在直觉很自信的时候
- **改约定时，先改保护约定的测试**——它们是绿的，所以最容易被忘掉

一个人写代码最大的风险不是写错，是**写错了却一直感觉良好**。
上面每一条，本质上都是在给自己制造"感觉不好"的机会。
